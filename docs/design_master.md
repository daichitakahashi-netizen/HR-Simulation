# 人材配置シミュレーションアプリケーション 設計マスタードキュメント

## 1. アプリケーション概要
特性の異なる3つの事業部（A:飽和、B:成長、C:新規）を持つ企業における「人材配置シミュレーション」を行うシステム。社員の能力（営業力・管理力・開拓力・育成力）や人件費データを元に、特定のビジネス目的（全社売上最大化、特定事業部の利益追求など）に応じた最適配置を算出し、経営・人事の意思決定を支援する。

## 2. UI/UX および 画面構成
単一画面（SPA）構成とし、ユーザーが条件を変更した際にシームレスに結果が反映される体験を提供する。

* **メインダッシュボード（シミュレーション画面）:**
  * **ヘッダー（サマリーパネル）:** 全社KPI（全社売上、全社利益、総コスト）を大きく明記。全社売上が前年度売上（58億円）を下回る場合は警告バッジ（赤色表示など）で視覚的にフィードバックする。数値はすべて「億円」単位を明記する。
  * **コントロールパネル:** 目的選択ドロップダウン（課題1〜4の切り替え）、特定人材のロック（固定）機能、100名/110名比較トグルスイッチを配置。
  * **事業部別カード (MatCard × 3):** A・B・C事業部ごとの詳細（配置人数、充足率、補正係数、最終売上、利益）をカード型で並べて表示。グラフ等の配色は事業部ごとに統一（A=青、B=緑、C=オレンジ）する。
  * **AI解説パネル:** 「どのスキルが活かされ、どのペナルティを回避したか」など、算出された配置方針とその理由を動的テキストとして自動生成・表示する。
* **非同期処理UI:** 重い最適化計算の実行中は画面中央にスピナー（MatProgressSpinner）を表示し、ユーザーの操作を一時的にブロックすることで状態をフィードバックする。

## 3. データフローと状態管理 (RxJS + Web Worker)
シミュレーションの膨大な計算負荷によるUIのフリーズを防ぐため、状態管理と計算ロジックを分離する。

1. **Trigger:** ユーザーによる目的（Objective）の変更、100名/110名モードの切り替え、または特定人材のロック操作。
2. **Smart Toggle (フェイルセーフ):** 110名切り替え時、Storeがデータ配列長を確認。データが100名分しかない場合は110名の再計算をスキップし、既存の数値を維持したままUIへ注記を表示する。
3. **Process (Web Worker):** メインスレッド（Store）からデータをWorkerへ送信。Worker内で「人数配分の全探索＋人材の最適割り当て（ハンガリアン法）」を実行し、最適解を算出（Web Workerが利用できない環境ではメインスレッドにフォールバック）。
4. **State Management (Store):**
   * `BehaviorSubject` と Angular Signals を組み合わせたハイブリッド管理。
   * 「100名での最適結果」と「110名での最適結果」をバックグラウンドで同時計算して保持し、UI側のトグル操作では再計算を行わず瞬時に表示を切り替える。

## 4. 計算ロジック・アルゴリズム仕様

### 4.1 基本定義と制約
* **全社人数 ($N$):** 100名 または 110名
* **最低配置人数:** A事業部 $\ge 30$名, B事業部 $\ge 20$名, C事業部 $\ge 10$名
* **適正配置人数（基準値）:**
  * $N = 100$名時: A = 40名, B = 35名, C = 25名
  * $N = 110$名時: A = 44名, B = 38名, C = 28名 ※（必要に応じて調整）
* **社員ロック仕様:**
  * ロックされた社員は「指定された事業部への配置を必須（固定）」とする。
  * 人数制約や最低配置人数と矛盾するロック指定が存在する場合、シミュレーション実行前にエラーを出力し処理を中止する。

### 4.2 アルゴリズムステップ（組合せ最適化）

#### Step 1: 人数配分の全探索パターン生成
* 最低配置人数を満たし、合計が $N$（100または110）となるすべての人数配分 $(N_A, N_B, N_C)$ パターンを網羅的に生成する。

#### Step 2: 人数制約下での最適社員割り当て
* 各人数配分 $(N_A, N_B, N_C)$ について、全社員を重複なくいずれか1つの事業部に割り当てる組合せ最適化を行う。
* **【厳格ルール】:**
  * 社員の適性順並び替えによる順次配置（貪欲法）、事業部ごとの独立ランキング配置、単一適性値のみに基づく割り当て、また不完全な局所探索によるスクリーニングは完全に禁止する。
  * 各パターンの充足率ペナルティを加味したコスト行列を生成し、最適割り当てライブラリ（munkres-js等）を用いて各人数配分における真の最適割り当てパターンを一撃で決定する。
  * 各人数配分において、選択された目的関数（全社売上最大化、特定事業部の利益最大化等）が最大となる割り当てパターンを決定する。

#### Step 3: 計算フロー・補正・最適解選定
各割り当て状態において、以下の順序で厳密に計算を行う（※計算高速化のため社員貢献度はループ外で事前計算する）。

1. **社員貢献度:**
   $$ \text{社員貢献度} = (\text{営業力} \times w_{sales}) + (\text{管理力} \times w_{mgmt}) + (\text{開拓力} \times w_{dev}) + (\text{育成力} \times w_{grow}) $$
2. **事業部能力値:** 属する社員の貢献度合計
3. **基本売上:**
   $$ \text{基本売上} = \text{基準売上} \times \left(1 + \frac{\text{事業部能力値}}{100} \times \text{成長係数}\right) $$
4. **充足率と補正:**
   * $\text{充足率} = \frac{\text{配置人数}}{\text{適正人数}}$
   * 補正テーブル（design_master.md 内の係数表）に基づき「不足補正」「過剰補正」を取得。
   * $\text{最終売上} = \text{基本売上} \times \text{不足補正} \times \text{過剰補正}$
5. **事業部利益・全社利益:**
   * $\text{事業部利益} = \text{事業部最終売上} - \text{事業部人件費コスト}$
   * $\text{全社利益} = \text{A利益} + \text{B利益} + \text{C利益}$
   * ※人件費コストは人件費の3倍、単位は100万円単位とする。

全パターンの中から選択された目的関数の値が最も高い配置を「真の最適解」として選出する（タイブレーク時は事業部Aの売上優先）。

### 4.3 局所解防止と検証要件（48/42/10対策）
* 100名・ロックなし・全社売上最大化の条件において、期待解（例：A=40, B=40, C=20）が選出されることを確認するテスト用内部検証ロジックを保持すること。
* 貪欲法で発生しやすい局所解（例：48/42/10）と真の最適解の評価比較値を内部で算出・検証可能とすること。

## 5. 開発ロードマップ

* **Phase 1: コアロジックの改修（アルゴリズム刷新）**
  * `munkres-js`ライブラリを導入し、基本スコアをループ外で事前計算する構成にする。
  * `simulation-engine.service.ts` および Worker の最適化処理を「人数配分の全探索＋最適割り当て」ベースに書き換える。
  * 100名データで「全社売上最大化」を実行した際、局所解（48/42/10）ではなく、仕様に基づく真の最適解が数秒で安定して算出されることを担保する。
* **Phase 2: UI/UXとStoreの結合・調整**
  * 構築済みのStoreと新Engineを連携。
  * 画面上でシミュレーション条件を変更した際、ローディング表示を適切に挟みつつ、新しい配置結果と「配置の理由（生成テキスト）」が正しく描画されることを確認する。
* **Phase 3: 追加採用パターンのUI統合と仕上げ**
  * 100名と110名の結果を比較できるUI（Smart Toggle）の最終調整。データ不足時のフェイルセーフ処理が正常に機能することを確認する。
  * 特定人材のロック機能の動作確認。
  * 採用前後の売上・利益の差分が、経営・人事視点で一目でわかる状態を完成させる。
